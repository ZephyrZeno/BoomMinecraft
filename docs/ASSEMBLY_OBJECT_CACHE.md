# 汇编对象增量缓存

v108 的上层自动翻译任务身份还包含 `native/runtime` 中全部汇编源码摘要。运行时契约变化会触发重新生成／验证批次元数据；字节一致的 MASM 单元仍可复用下述 COFF 缓存。这两层身份分别约束运行时语义与汇编产物，不会因内核实现改变而误用旧的成功验证记录。

这项加速只覆盖构建中的 MASM → AMD64 COFF。Java → 汇编仍由自研后端执行；游戏运行时和游戏侧优化仍为汇编。缓存不会增加已有运行时功能，也不代表 Minecraft 已启动。

## 接入位置

`src/assembly_cache.rs` 被 `batch_compile::write_unit` 和共享数值内核调用。普通 Java 分片、分派、类型、静态状态和已接入 native 家族经同一入口汇编，因此不需要为各个方法登记缓存。默认目录为当前项目的 `.boom/assembly-object-cache/v1`。旧批次不会被改写或导入为可信缓存；第一次使用新流程需要实际汇编。

每轮仍重新解析、生成 MASM 和记录实际源来源。缓存键只处理下一步的机械汇编，包含缓存版本、完整 MASM 的 SHA-256、`ml64.exe` 的 SHA-256 和固定 AMD64 非调试选项。隐式 `ML` 环境选项被移除。键不包含 Rust 编译器版本：升级翻译器后，只要最新输出逐字节相同，已有 COFF 仍可复用。

汇编外部符号所引用的布局、运行时和调用假设仍须在本轮独立校验与链接中检查。相同的重定位对象可以链接到更新后的兼容服务；缓存命中不证明新服务语义或 ABI 正确。完整独立校验、最终链接和实际执行均不跳过。

## 发布与恢复

缓存条目将键身份、对象完整摘要、原汇编日志与 COFF 放在同一个文件，临时文件完成后原子发布。并行生产相同键时保留已完整发布且摘要有效的条目。恢复时校验身份、文件大小、AMD64 可重定位头和完整对象摘要，再复制至新批次；不使用硬链接，修改新批次文件不会污染缓存。

损坏、截断、身份不同的条目一律视为未命中，重新调用汇编器并尝试修复。汇编失败不发布条目，缓存写入失败不伪造汇编成功。源文件和汇编器在操作后再次核对，避免构建过程中变化的输入被发布。缓存的结构头检查仅为完整性预检，不能替代已有的完整 COFF、来源和链接检查。

含外部 include、二进制输入、环境、文件名或时间相关构造的文本保守绕过缓存。当前批量生成器使用已内联的自包含模块；未实现一般 MASM 预处理依赖追踪。调试信息、跨汇编器版本复用、跨机器工具信任和普通方法代码生成缓存不在本项范围。

当前检测按保守的文本匹配工作，方法来源注释中含 `Environment` 等字样也可能被绕过。绕过仍会正常调用汇编器，不产生兼容缺口；后续可用词法识别减少这类重复工作。

## 开发命令

```powershell
./target/release/boom.exe assemble-unit `
  --source <自研后端生成的.asm> --output .boom/example/unit.obj

./scripts/Test-AssemblyObjectCache.ps1
```

`assemble-unit --no-cache` 可执行无缓存对照，`--cache <目录>` 可指定隔离测试缓存。命令输出真实汇编结果和 `hit / miss / bypassed / disabled`；失败以非零退出码返回。该命令只用于开发，启动器不增加编译按钮。

批次 summary 保持 schema 19，在单元中附加 `assembler_cache`，共享数值内核附加 `numeric_kernel_assembler_cache`。这些字段记录构建来源；所有游戏／世界／完整运行时状态保持原有验收要求。编译工作者并行和缓存加速不能记作游戏多核优化。

## 本轮验证

Rust 198 项、Python 146 项测试及 fmt／clippy 通过。原生缓存探针实际链接执行 16 个机器码夹具，验证路径迁移后的字节一致命中、源码变化失效、损坏重建／修复、失败不缓存、include 改变时重新汇编、禁用缓存对照和 8 工作者并发发布。它们是开发夹具，未执行游戏。

服务器真实输入冷构建的完整来源／COFF 独立校验通过。相同锁与 IR 的再次构建保持 877 个普通 Java 汇编单元摘要一致：总计 969 个单元含共享内核，其中 903 个命中且机器码完整摘要与冷构建一致，65 个保守绕过，1 个属性池因输出映像路径改变而失效重建。非命中对象比较了实际 COFF 导出／导入集合；未将它们宣称为字节一致，也没有重跑热批次的完整独立验证器。

本机两次均用 8 个编译工作者，编译阶段为 141.575 秒／104.937 秒，耗时约减少 26%。普通 Java 代码生成仍执行；这个对照不包含完整校验、最终链接或游戏启动耗时。客户端新缓存批次未在本轮重新构建，保留 v104 的既有验证范围；也未实测不同 Rust 编译器映像之间的热构建时间。
