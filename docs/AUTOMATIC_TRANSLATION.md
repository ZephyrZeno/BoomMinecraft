# 自动翻译与兼容收敛设计

## 原版 1.21.1 的原生启动验证

服务端及其依赖的锁定批次包含 53,660 个类。31,931 个方法声明没有 Java 字节码，另有 498,906 个方法带有字节码，其中 498,179 个已生成汇编，727 个尚未生成。启动验证从此批次选取需要链接的方法和类初始化描述符。普通 Java 目标可以根据真实运行命中的调用行自动纳入下一轮，也可在已验证的声明类中提前批量选择。提前选择只增加链接范围，统计执行进度时使用原生进程实际返回的记录。

v137 在同一 Windows x64 原生进程里链接了 20,248 个原始 Java 方法。主线程执行完 `System.initPhase1`，从原始 `VM.initLevel` 静态字段读到 1，再调用原始 `System.initPhase2(ZZ)I`。主线程在 Windows 文件系统的 `WinNTFileSystem.initIDs` 停下，后台线程在 `Reference.waitForReferencePendingList` 停下。退出前仍有一个监视器持有计数。Minecraft 的主方法、游戏窗口和世界仍未得到启动验证。

诊断程序按 Java 执行上下文记录命中的来源行。自动纳入主线程与全进程首个调用时，同时校验原生二进制报告、选择证明、诊断表和原始方法体。已通过校验的两个 MASM 目标文件可以直接用于下一步生成启动验证程序。源文件、汇编器或目标文件发生变化时重新汇编。首版启动器仍由玩家从“启动游戏”进入，开发验证保留在命令行。

Windows 的文件系统注册需要定位原始 `java.io.File.path`，还会向操作系统查询 `GetFinalPathNameByHandleW`。汇编服务执行原始 File 类初始化，按类摘要和已验证布局生成字段标识，同时保留可选系统函数的真实查询结果。后续文件操作可以共用这份信息。[OpenJDK 21 Windows 文件系统实现](https://github.com/openjdk/jdk21u/blob/master/src/java.base/windows/native/libjava/WinNTFileSystem_md.c)

v139 的实际原生运行已经完成上述文件系统注册。镜像纳入 20,266 个 Java 方法，主线程推进到 `SystemModules$default.moduleDescriptors`。引用线程进入真实等待并在关闭时完成受控退出，后台终结线程停在 `Object.wait0`，最终堆、帧和线程登记均已清理。模块描述符方法已有汇编产物，现已由自动纳入程序依据实际来源行加入后续验证。

v141 增加按加载器和包名预选的方法。`Invoke-NormalVmThreadBootstrap.ps1` 的 `-PreselectPackage @('bootstrap:java/lang/module','bootstrap:jdk/internal/module')` 与 `-SourceSelectionDirectory` 一起使用；底层命令 `preselect-diagnostic-java.py` 可重复传入 `--package`。选取严格匹配加载器和 `/` 分隔的包边界，校验原始类索引、批次身份及归档摘要，在方法预算内优先纳入整个声明类的已生成 Java 方法。不会增加类初始化根、补造 native 或把预选计作执行。实际锁定服务端输入匹配 91 个模块系统类；无此选项时保留原有规则。三个新增边界回归测试已通过。

v127 新增[原始终结策略查询](FINALIZATION_POLICY.md)，保留 Java 字节码批次及当前汇编运行时。实际启动两个原版后台工作者后，共享来源诊断前沿推进到 Object.notifyAll。独立[引用传输内核](REFERENCE_PENDING_RUNTIME.md)完成真实等待、停止唤醒和根保护测试，尚未接到原版 native；正常通知、监视器展开与完整游戏仍需继续补齐。

v98 已接入[正常 String 拼接展开器](NORMAL_STRING_CONCAT.md)：服务端 9,991／客户端 10,387 个现场自动生成真实汇编，参与同一批量校验、依赖扫描和兼容任务规划。执行测试范围包含内核及准备夹具中的实际适配器；完整原始引导和游戏仍未启动。Lambda 等剩余协议继续由规划器报告，尚未自动展开。

目标是在现有自研后端之上，让普通 Java 代码、元数据和共享调用规则自动成批生成汇编，把需要实现平台或 VM 语义的工作集中到协议层。首个目标仍为原版 Java 版 1.21.1；全量生成、汇编、链接、执行、创建世界分别验收。

新增的[自动收敛程序设计与命令](AUTOMATIC_COMPLETION.md)将这条路线细化为按家族任务、入口扫描、来源验证和跨轮请求比较。`Invoke-AutomaticTranslation.ps1` 已接入 `plan-translation-completion.py`；它输出完整任务清单，未实现的 native／bootstrap 仍要求真实汇编服务或降级规则。

进一步的[协议展开层设计](AUTOMATIC_COMPLETION.md#下一层先展开机制再批量编译2026-11-25)定义了将 Lambda、字符串拼接和 Record 展开为普通 IR／正常合成类的接口、前置类型注册及增量缓存。调度器 schema 3 已接入 `plan-protocol-expansion.py`，逐现场核对真实来源并输出结构计划；字符串拼接已于 v98 接通正常汇编规则，Lambda 和 Record 的正常布局展开尚未实现，单独的预检不生成游戏汇编或消除链接缺口。

## 输入与流水线

v125 增加两项离线读取优化：独立闭包校验只索引一次大汇编文件中的描述符／异常表／分派数据，再逐段核对完整内容与摘要；JDK 原始类可从已有 JMOD 读取，但每次仍核对锁定类 SHA256，缺少或不匹配的副本继续读取原始提取镜像。新旧真实映像验证记录和两组反射元数据均比较一致，未删掉分派行、改写 Java 字节码或更换游戏运行时。

1. 锁定原版、库和 JDK 的来源、加载器身份及散列，复用已校验的计划和符号 IR。
2. 通过现有 `compile-translation` 并行翻译所有含 Code 的 Java 方法。一个方法失败不阻断其他方法。
3. 自动生成字符串常量、对象布局、类型／字段表、静态存储及类初始化依赖。
4. 新的契约生成层收集成功生成方法的所有绑定请求，去重并按语义生成。首先处理普通 `invokevirtual`／`invokeinterface`；动态引导和 native 进入按协议归组的兼容清单。
5. 独立校验来源、选择结果、汇编与实际 COFF 定义。未生成的目标仍保持未定义符号，禁止生成默认返回值或空成功函数。
6. 根据真实启动入口收集链接闭包和所有缺口，按依赖实现协议，重复生成和验证。通过原始 System 启动、Minecraft 入口和隔离世界测试后，才交付可启动版本。

翻译和生成可以使用 Rust；游戏执行、分派和后续运行时优化只使用汇编。编译工作者的并行度不算游戏多核优化。

## 通用虚调用生成

成员解析继续复用来源校验后的加载器、包访问、继承和方法选择规则。每个现场保留符号所有者、已解析声明、接收者约束、调用类型和原始方法身份。接收者约束包含 protected 访问边界以及数组类型，不能用字节码验证器放宽后的接口赋值规则替代。

按“已解析声明＋调用类型”共享选择表。同一声明被许多子类常量池引用时，接收者检查留在各现场，选择表只生成一次。通过类祖先关系的倒排索引枚举相关接收者，避免为每个调用点扫描整个输入。表内记录实际 Java 方法包裹入口或原生声明符号；包裹入口保留 synchronized 语义，普通实例调用不额外初始化声明接口。

运行时汇编先取得实际类型，验证现场接收者约束，再按来源类 ID 二分查找目标。数组保留真实类型／协变检查，并选择 Object 中继承的方法；数组 clone 继续使用独立协议。找不到目标、抽象方法和访问错误保留不同错误种类。空接收者和已有异常不调用目标。

这遵循 [JVMS 21 方法选择](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.6) 和 [调用指令契约](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.invokeinterface)。静态表只适用于当前锁定映像；可选依赖、未知加载器和模组新增类型不能假装包含在闭包里。

## 兼容清单

兼容报告同时保留原始绑定和分组结果：native 按实际声明归组，动态调用／常量按 bootstrap 协议归组，特殊字面量按种类归组。记录影响的符号／方法数量和来源样例。分派选择表另列所有目标，区分已经生成的 Java 目标、缺少 Java 代码产物的目标和未绑定的 native 目标。

“生成适配器”只说明调用规则已生成，不能把其尚未实现的 native 目标或下游依赖算作完成。全输入中的可选功能缺口也不能直接称为启动阻塞；实际启动优先级由入口闭包和执行证据决定。

Java native 声明只有签名，没有平台实现。任意第三方 native 和未知 bootstrap 需要明确语义或兼容实现；自动工具负责把同一规则应用到所有现场，不能从签名自动推导行为。

开发调度程序为 `scripts/Invoke-AutomaticTranslation.ps1`。输入 `-Pipeline <包含 side/catalog/plan/ir 的 JSON>` 与 `-Lock <原始输入锁>`，一次执行来源校验、并行代码／契约生成、实际汇编、独立验证和 `compatibility-summary.json` 输出。其缓存绑定输入和工具散列；复用时重新校验来源契约及 COFF，损坏产物自动在新的隔离目录重建，不覆盖旧证据。它不启动游戏，也不安装工具。

v90 新增 `-ResumeBatch <本项目 .boom 内的产物目录>`：核对编译器、锁与 IR 身份后，跳过重复代码生成，直接执行新的完整校验。报告同时标记续验和缓存复用，失败不会发布成功记录；不能以此复用另一个编译器或输入下的对象。

## 缓存、模组与启动器

缓存至少绑定输入锁、类／Code 散列、编译器身份、加载器和变换链版本、已解析声明、接收者集合、对象布局、运行时及目标 ABI。新增子类或变换方法时，共享分派表和引用它的链接结果必须失效。首批生成保守重建契约；方法级选择性机器码复用和任意动态加载仍是后续工作。

玩家界面继续只有启动流程。输入准备、批量翻译、契约生成、缓存检查及最终链接由该流程自动调度，开发命令不转化为玩家的编译按钮。当前尚未完成最终启动流程和整版运行时，不因新增批量生成层宣称游戏已启动。

## v89 实现和真实输入验证（2026-11-25）

`batch_dispatch.rs` 已接入 schema 6。服务器／客户端分别自动生成 321,711／358,825 个虚调用现场，复用 107,909／119,555 张表，包含 1,786,023／1,911,911 行接收者选择。新增 24／26 个 MASM 单元全部实际汇编成功，独立校验器重新核对原始符号常量、方法声明、加载器、protected 与数组约束、选择结果、编码汇编和 COFF。完整批量生成含汇编耗时 124.332／127.650 秒，独立校验另计；这是本次构建记录，不是游戏性能基准。

候选对象的未解析符号从 v88 的 373,848／418,531 降为 52,499／60,127。新表会引入原来未直接引用的目标，因此不能把生成现场数简单当成净消除符号数。分派所选目标中仍有 143／202 个 Java 方法没有汇编产物，322／322 个 native 目标未绑定；另外还有其他直接调用的 native、bootstrap 和字面量契约。服务器／客户端兼容清单分别为 1,829／4,424 组，全输入影响排序不代表启动必经次序。

选定原始 ByteBuffer.isDirect 现场及完整共享表按字节复制后链接运行；四种实际 ByteBuffer 类形状与 JVM 对照，每侧 8 个工作者执行 16,416 次调用。另验证 31 个内核错误场景、原始 Object.equals 在数组上的两次调用，热分派不分配游戏堆对象。这些接收者通过汇编堆分配源布局，没有运行其 Java 构造器；接口分派只完成全输入选择／汇编验证，尚未在本次探针执行。原始六枚举／四常量类初始化回归通过。System 完整启动、Minecraft、世界和自动回收仍未完成。

## v91 原生家族与入口闭包

## v92 标准流根发布

同一 System 家族规则自动提供三个源 native setter，直接连接源字段静态根；原始注册表仍为三项，没有将独立 JNI 入口塞入该表。源类型表 ABI2 和旧 ABI1 均通过执行验证，新入口覆盖并发发布、错误引用拒绝与显式根图回收。选定原始 ByteArrayInputStream 实例方法已执行；正常类初始化、输出流构造和实际 I/O 仍是兼容前沿。这些运行时协议需要真实实现，不能由生成一个未绑定方法的汇编外壳取代。

## v93 自动依赖展开

入口选择器已能沿虚调用／接口的完整共享表继续选择目标，不必逐个列出目标方法。选择范围包含全部静态接收者行与数组目标，不会把尚未实现的 native 默认为可执行。新增函数／类描述符／分派数据的位置索引，同一 System 直接扫描用时 7.838 秒，缺口身份与原因保持一致；源 ByteBuffer 调用已通过自动选择、链接与执行验证。

扩大后的保守扫描自动选入 327,096 个 Java 方法和 219,613 个调用现场，25,532 个前沿按协议或方法来源类归为 396 个候选组。Class、Lambda、字符串拼接和 record 方法四类规则涉及 23,310 个现场；实现通用规则后可统一覆盖这些请求，但每组实现量不等，且并非所有可选实现都在实际启动路径上。位置索引将同一扩大扫描由 1,494.087 秒降至 597.487 秒，全部前沿记录逐项一致。

默认扫描会展开已生成的分派；`--direct-only --scan` 可保留旧范围，`--contract <源现场符号>` 可用于单独验证规则。全行静态展开可能把实际启动不使用的可选实现带入，未知动态目标仍保留前沿；应据运行证据安排兼容优先级，不能把宽泛清单当作游戏启动必经次序。启动器仍只有启动入口。

## v94 Class 家族与兼容任务

Class 字面量现在统一由源 Class 字段布局和规范镜像池提供，服务器／客户端分别生成 8,400／9,089 个现场，覆盖 109,803／123,477 种已提供类型。八个核心 native 使用同一个源形状服务，普通 Class 的 represented type 不覆盖 Java 字段。原始 Enum.getDeclaringClass 的执行链已调用原始 Java、Object.getClass、Class.getSuperclass 和规范 Class 字面量，证明这是一条实际运行的通用规则。Class 自身的完整初始化、原生注册和模块引导仍未完成。

新的任务规划自动合并直接协议和未绑定的分派目标，保存全部符号、原始声明和精确协议。实际两侧输入分别归为 410／580 个家族任务；服务器直接入口扫描的 769 个前沿中，605 个是已有分派规则的继续展开动作，剩余 164 个请求逐项归入兼容任务。这是静态分析与排程结果，不是必须启动依赖数量或运行时功能完成度。
