# 引用待处理传输与 VM 退出衔接

v134 的原版工作者实际到达 `Reference.waitForReferencePendingList()`。v139 将它和同一原始类的 `hasReferencePendingList`、`getAndClearReferencePendingList` 接到汇编服务。适配器校验 bootstrap 加载器、原始类摘要、三个方法的签名、静态 native 标志和原生帧，使用每个游戏进程独立的待处理列表。

VM 拥有者在启动 Java 工作者前创建列表。关闭时，汇编等待内核唤醒等待者，适配器以 TLS 记录收到停止信号的原始执行上下文。工作者完成 Java 栈展开后，同一系统线程才可消费该停止记录。汇编边界释放当前线程拥有的监视器，保留 VM 异常配置，并让线程继续执行原始退出回调。工作者加入后，VM 才销毁列表。v138 独立适配器测试实际测到一次有工作的正常唤醒、八次受控取消和八个已释放的监视器，异线程或其他上下文均无法消费停止记录。自动发现弱引用和完整游戏内存回收仍需实现。

v129 验证了 `native/runtime/reference_pending.asm` 在独立 DLL 和 87 源文件汇编运行时中的行为。v138 的 88 源文件运行时增加了监视器退出内核，使用同一 DLL 重跑了引用传输和监视器并发测试。

## 已实现的内核

每个池持有属于一个堆的待处理批次头、待处理事件和停止事件。发布要求非空且属于该堆的对象；已有未取走批次时返回 BUSY，由发布者继续保有其批次和根。取走操作在锁内清除头和事件。等待不消耗批次，空队列通过真实 `WaitForMultipleObjects` 无限等待；唤醒后重新检查队列，处理其他消费者先取走批次的竞争。

停止请求设置独立事件，唤醒等待者并返回 Win32 `ERROR_OPERATION_ABORTED`（995），不返回正常待处理工作成功。停止后的读取、发布与等待同样区分中止状态。只有请求停止且全部等待者退出、根租约结束后才能销毁池；VM 仍必须先加入所有生产者和消费者，再销毁池或其借用的堆。全局短锁保护池登记与注销，未知或已注销指针不会被当作池解引用。

根租约返回包含批次头单元的 Span16，绑定申请租约的 OS 线程，并阻止发布、取走、等待、停止和销毁。当前显式、静止堆回收可以在租约期间使用该根；这不补足活动 Java 栈根、安全点、弱引用判定或自动收集。批次内发现链必须由将来的来源适配器／收集器按原始字段映射建立。

## v129 时的接入设计

需从锁定 bootstrap `java/lang/ref/Reference` 的原始声明生成 getAndClearReferencePendingList、hasReferencePendingList 和 waitForReferencePendingList 绑定，保留原始 ReferenceHandler 的循环、处理锁及入队逻辑。VM 在 Java 工作者开始前建立池，在退出时先请求停止，再等待所有工作者和信号回调，最后销毁池、帧、注册表及堆。

995 需要转换为经过真实 VM 停止状态认证的内部控制展开，和 Java Throwable、来源诊断停止分别处理。取消不能计作正常 Java run 完成；原始 Thread.exit 仍需执行。现有异常匹配只处理 kind16，Java 同步块的退出还依赖字节码 finally，控制展开需要正确处理本线程遗留的监视器；不能仅清除 Context。同步方法本身已有独立退出封装，但这不覆盖全部同步块和 Object.wait。Context32 的偏移24已用于 VM 异常配置指针，不能挪作诊断行或停止令牌；新增诊断信息应使用独立记录或经过完整兼容设计的新协议。

终结线程还需要真正的 Object.wait／notify、超时、中断和监视器恢复协议。启用策略查询本身不实现终结对象登记、待处理引用发现或终结执行。完成这些同步和关闭契约前，不将原版后台线程的进入计作正常生命周期完成。

第二阶段的变换后类不能复用原始 bootstrap 原生绑定。发现链／字段地址／类型验证继续使用来源和加载器身份校验过的字段映射；类布局或变换链改变时，重建并重新验证相关适配器与派发表。内核不硬编码 Java 类偏移。
